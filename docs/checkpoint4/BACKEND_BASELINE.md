# Backend contract findings for Globexa UI Lab

Inspected read-only on 2026-09-09. Repository: GlobexaTech/Globexa_CRM_Python. Verified local HEAD: `0d030cf4d0f0f00cec05f443d91c41f44ee7ba43`. Sources: actual registered routes, schemas, middleware, services, RBAC and events, plus FRONTEND_API_CONTRACT.md. OpenAPI was generated from this checkout in memory; no application runtime or external provider request was made. Findings describe implemented contracts, not end-to-end frontend verification.

Abbreviations: API = `/api/v1`; OPS = `/api/v1/operations`. All IDs are UUIDs. CRUD below means POST collection (201), GET collection (200), GET item (200), PATCH item (200), DELETE item (204), unless stated otherwise.

## Cross-cutting contract

- Authenticated calls should send `Authorization: Bearer <access-token>` and `X-Tenant-ID: <tenant-uuid>`. Middleware verifies active user, active tenant, current membership and JWT/header tenant agreement. A changed tenant header alone cannot switch tenancy. Auth/login/register/google/refresh and signed public unsubscribe are exceptions; signed hooks use their provider contract.
- Login is POST API/auth/login with `application/x-www-form-urlencoded` fields `username=<email>&password=...`, not JSON. Register uses UserRegister JSON. Login/register/refresh/switch-tenant return `{access_token,refresh_token,token_type,expires_in}`. POST API/auth/refresh takes `{refresh_token}`. GET API/users/me includes memberships; GET API/auth/me returns only UserResponse. GET API/auth/tenants returns `[{id,name,slug,role,is_default}]`. POST API/auth/switch-tenant/{id} returns replacement tokens. Logout returns success and the client must discard tokens.
- Legacy collection lists use `page=1&page_size=20`, response `{items,total,page,page_size,total_pages}`. New OPS lists use `limit=50&offset=0` (search default20), response `{items,total,limit,offset}`. Pipeline/stage/provider lists are plain arrays. Customer360 has its own `pagination` object.
- HTTPException errors: `{detail}`; validation errors: `{detail:"Validation error",errors:[{loc,type}]}`; provider exceptions: `{detail:"Provider operation unavailable",code}`. Quota/permission denial is403; tenant-resource absence404; idempotency/state409; invalidinput422; rate429 with Retry-After. Unsupported operation checks also return501. Unconfigured providers can return503.
- Strict OPS request models reject unknown fields. Numerous legacy requests and OPS responses are generic dicts; generated OpenAPI types are insufficient for their entire payload.
- No SSE/WebSocket live-update API was found. Poll jobs and invalidate/refetch related records after completion.
- Writes are Redis rate limited. Do not repeatedly resubmit quota errors or automatically retry an uncertain external send.

### Exact asynchronous and idempotency rules

`Idempotency-Key` is required (8–100 chars) ONLY by:

| Endpoint | Response |
| --- | --- |
| POST OPS/conversations/{id}/messages | 202 JobResponse |
| POST OPS/integrations/{id}/sync?cursor=... | 202 JobResponse |
| POST OPS/ai/requests | 202 JobResponse |
| POST OPS/ai/batches | 202 array of JobResponse |
| POST OPS/tools/{name} | 200 dict; tool execution itself is synchronous, with durable idempotency for mutations |

POST OPS/jobs/{id}/approve and /retry return202 JobResponse without an Idempotency-Key header. POST OPS/events/{id}/retry returns202 `{id,status:"queued"}`, also without that header. Campaign launch/schedule/pause/resume/cancel return200 campaign state, though launch/schedule lead to background delivery; they take no client idempotency header.

JobResponse: `{id,kind,status,attempts,result,error_code,created_at}`. States are `pending,retry,running,completed,failed,cancelled,unknown,awaiting_approval`. GET OPS/jobs supports kind/state/limit/offset; GET OPS/jobs/{id} polls a job. Other actors' jobs require audit permission. Retry accepts only failed automation/sync jobs owned by the original actor and attempts<3. Unknown is not safely retryable. Approve applies only to AI hook suggestions, not arbitrary task approvals.

## Role translation

Backend enum is `owner,admin,sales_manager,sales_executive,marketing,viewer,ai_agent`. Labels such as Manager and Sales Agent require an explicit display-name mapping to sales_manager and sales_executive. An AI Agent is NOT an all-powerful user.

| UI capability | Current backend grants |
| --- | --- |
| Basic CRM reads (leads/contacts/companies/deals/tasks) | owner/admin/sales_manager/sales_executive/viewer; marketing has all except tasks; ai_agent only leads |
| CRM writes | owner/admin/sales_manager/sales_executive; marketing leads/contacts/companies, not deals/tasks |
| Conversations read/write/send | owner/admin/sales_manager/sales_executive/marketing |
| Workflow edit/enable | owner/admin only; sales_manager read only |
| Analytics permission | owner/admin/sales_manager/marketing, with extra view checks as above |
| Campaign edit/launch | owner/admin/sales_manager/marketing; sales_executive/viewer read only |
| Integration read/write | owner/admin/sales_manager/marketing |
| AI capabilities | owner/admin/sales_manager/sales_executive all six; marketing lead_summary/campaign_draft; viewer none; ai_agent none (only leads:read + ai:chat) |
| Notes read/write | owner/admin/sales_manager/sales_executive both; marketing/viewer read only |

UI role checks are only presentation: server current membership checks remain authoritative. Some legacy routers use role thresholds while OPS services use permission strings; don't infer every operation from hierarchy alone. No dynamic permission list endpoint is presently available.

## AI and event/architecture mapping

Capabilities and entity/output:
- lead_score → Lead → score0–100, confidence0–1, reasons[1–10]; persists lead.ai_score and reasons.
- lead_summary → Lead → summary; persists lead.ai_summary.
- next_best_action → Deal → action,confidence,reasons; recommendation only, no stage mutation.
- reply_analysis → Message → classification(interested/not_interested/question/objection/meeting_request/unsubscribe/other),confidence,summary.
- campaign_draft → Campaign → subject,body; draft only, not sent.
- proposal_draft → Deal → subject,body,proposal_id; persisted Proposal draft with provenance.

All run through configured gateway, AI credit quota, current actor permissions, durable usage and AIInsight. Job result includes validated output (and proposal_id when applicable), not an insight_id. Approved tools: search_leads,get_customer,get_pipeline,create_task,update_lead,create_note,draft_email. No arbitrary SQL/code or autonomous sending. There is no current generic conversational AI endpoint.

Registered domain events: lead.created,lead.updated,contact.created,contact.updated,deal.created,deal.stage_changed,task.created,task.completed,task.overdue,note.created,activity.created,campaign.started,campaign.completed,message.received,message.sent,integration.synced,ai.completed,automation.completed,conversation.created. No company.created/updated events. Events are durable outbox→Celery→subscriber receipts, not browser event streams. Workflows support seven triggers: lead.created,lead.updated,deal.created,deal.stage_changed,task.overdue,message.received,campaign.completed. Actions: create_task,update_lead,update_deal,add_note,send_email,assign_owner,invoke_ai; max10, conditionsmax20, bounded chains. Campaign trigger subset: lead.created,contact.created,deal.stage_changed,task.completed.

Existing architectural entities reused: Tenant/User/Membership; Company/Contact/Lead; Pipeline/Stage/Deal; Task/Note/Activity; Campaign/Audience/Template/Sequence/Trigger/Recipient/Stats; Integration/OAuthToken/Credential/Webhook/SyncLog; Workflow/Trigger/Condition/Action/ExecutionLog; Conversation/Message; AgentDefinition; Proposal; DomainEvent/EventDelivery/AuditLog/AIUsageLog; entitlement/usage catalogs. CP3 adds Participant,AnalyticsEvent,OperationJob,AIInsight,OAuthSession,WorkflowRevision. Presence of an entity is not proof of a complete UI-facing CRUD or execution feature.

## FRONTEND_API_CONTRACT.md discrepancies / integration gaps to retain in audit

1. “Async requests and tools require Idempotency-Key” is too broad. Exact header-required list above; approve/retry/replay and campaign state endpoints are exceptions.
2. “Lists use {items,total,limit,offset} where declared” omits the equally important page/page_size legacy contract. Do not build one implicit pagination adapter.
3. “Job results identify persisted insight/proposal records” overstates insight lookup: AI result lacks insight_id; proposal_draft includes proposal_id.
4. “Use current role permissions from server” lacks an implementable permissions endpoint. Server exposes roles/memberships, not a current expanded permission set.
5. Campaign fine-grained audience/template/sequence permissions are enforced by legacy routes; OPS configure_campaign checks campaigns:write only. Its request is richer than that one permission name suggests.
6. Error list omits400 and501; OAuth invalid/expired state400 and unsupported provider501 are implemented. Custom validation envelope differs from default FastAPI HTTPValidationError shape advertised by automatically generated OpenAPI.
7. OPS campaign status running versus legacy sending needs normalization; neither should silently overwrite the other in a global store.
8. OpenAPI is disabled remotely when debug=False, including /openapi.json. Use the CI-exported schema artifact instead of assuming production schema fetch. X-Tenant-ID is enforced in middleware and not fully represented as a per-route OpenAPI parameter/security scheme.
9. Several requested experiences have no backend endpoint: generic AI chat/workforce agent management, saved/custom reports, session/security preference management, and live updates. They must be marked unavailable/mock/proposed rather than inferred from model/permission names.
10. Customer timeline endpoint returns the full aggregate, not only timeline entries. Analytics response-time window differs from selected event date range. Expose both limitations.
11. Provider cards expose supported code capabilities and live_verified:false, not whether this deployment has OAuth configuration. A supported Gmail/Outlook card still needs configured/connected/error states from actual lifecycle calls.
12. Existing /foundation/workflows and /foundation/search coexist with current OPS routes; no global route deletion occurred. New UI must deliberately use OPS executable workflow/search contracts.

Potential separate backend follow-up found by static reading: deal move returns a refreshed ORM Deal directly while normal deal CRUD uses scalar DTO serialization; nested optional response relations can encounter asynchronous lazy-loading errors. This route was not runtime-tested during this read-only frontend audit and should be exercised before shipping kanban drag/drop. Do not present this as an observed runtime failure.
