## Data model and architecture

Existing Tenant/User/Membership, Company/Contact/Lead, Pipeline/Stage/Deal, Task/Note/Activity, Campaign/Template/Sequence/Trigger/Recipient, Integration/Credential/SyncLog, Workflow/Trigger/Condition/Action/ExecutionLog, Conversation/Message, DomainEvent/SubscriberReceipt/AuditLog, AI and entitlement entities are reused. There are no parallel replacement CRM tables.

Migration `011_crm_operations` adds six tenant tables:

| Table | Purpose |
| --- | --- |
| conversation_participants | Conversation addresses and names |
| analytics_events | Idempotent event facts for operational reporting |
| operation_jobs | Durable operations, attempts, actor, idempotency key and state |
| ai_insights | Validated AI output and provenance linked to jobs |
| oauth_sessions | Single-use, expiring state and encrypted PKCE verifier |
| workflow_revisions | Immutable versioned definitions |

It extends conversations/messages with channel, customer/thread relations, delivery state, attachments metadata and unread state; workflows with owner; execution logs with version, snapshot and attempts. It adds scoped composite foreign keys, job indexes and full-text indexes. Migration `012_activity_relation` repairs the existing ORM/database mismatch for Activity.campaign_id. The suppression-list provider enum mapping now matches its existing PostgreSQL type. Historical migrations 001–010 are unchanged.

Head: `012_activity_relation`. Model inventory: 62 tables; FORCE RLS covers all 57 tenant_id tables plus users and tenants. The three remaining model tables are global product/plan catalogs. The explicit inventory is in `RLS_TABLE_INVENTORY_CHECKPOINT_3.md`. New relations are checked in services and constrained in PostgreSQL. Customer sections, analytics, search, jobs, tools and workers enforce permissions as well as tenant scope.

## CRM services and API

See `FRONTEND_API_CONTRACT.md` and generated OpenAPI for route/request details. Existing CRUD remains available; `/api/v1/operations` supplies Customer 360/timeline/export, conversations/messages/read state, campaign planning and lifecycle, workflows/executions, provider OAuth and sync, AI requests/batches/proposals, jobs/approval/retry, event replay, six analytics views, ten-entity search, activities and approved tools.

Customer 360 links customer identities, deals, tasks, notes, activities, campaign participation, conversations/messages, AI insights and related integration activity. Each section requires the corresponding read permission. Task and deal serialization no longer triggers asynchronous lazy-loading during response construction. Task, note and activity writes use their authoritative write permissions.

Conversations support email, WhatsApp and social records and participants. Only configured email adapters can deliver outbound messages. Inbound ingestion persists provider IDs, thread identity, direction, timestamps and attachment metadata with duplicate protection. Messages and read state appear in Customer 360.

Campaign plans snapshot explicit contacts or company contacts, templates, provider and ordered steps. Broadcast, relative-delay sequence and event-triggered plans use persisted recipient jobs. Lifecycle includes schedule, launch, pause, resume, cancel and calculated completion. Worker execution rechecks permissions, campaign state, earlier steps, quota, opt-out and suppression. Duplicate addresses receive one step; reply/bounce/opt-out prevents later steps. Campaign sends create conversation history. HTTPS signed unsubscribe links display confirmation on GET; POST applies opt-out and suppression, including one-click provider requests. No real mass campaign was sent.

## Events, retries and workers

Domain events persist transactionally with CRM mutations. The event inventory includes lead.created/updated, contact.created/updated, deal.created/stage_changed, task.created/completed/overdue, note.created, activity.created, campaign.started/completed, conversation.created, message.received/sent, integration.synced, ai.completed and automation.completed. Payloads use safe IDs and selected state fields, not credentials or full customer content.

Analytics and CRM subscribers use durable receipts and locked event processing. They collect metrics, update conversation state, reconcile campaign replies/unsubscribes, trigger campaigns/workflows and create approval-required AI hooks. Signed webhook ingress routes a verified stored integration to a durable sync job. Operator event replay resets publication; completed receipts prevent duplicate effects.

`foundation_tasks.deliver_event` retries subscriber failures. `crm_tasks.crm_tick` schedules due campaigns, overdue-task events and integration sync, then dispatches bounded batches; `crm_tasks.execute_operation` runs each job in a tenant database context. Celery Beat's tenant dispatcher invokes both event publication and CRM scheduling. Legacy worker names remain registered but delegate to this engine or reject raw, unaudited sends/AI calls.

Jobs retain actor, immutable input, idempotency key, result and attempt history. A tenant advisory lock serializes enqueue; reusing a key with different input or actor returns 409. Worker checks use current membership permissions. External sends commit their running claim before I/O: a crash, network ambiguity or provider 5xx becomes `unknown`, never an automatic duplicate send. Provider throttling has bounded retry. Internal automation actions use a transaction savepoint; failed workflows can be retried safely. Failed sync/workflow jobs allow at most three attempts by their initiating actor. Events support explicit receipt-safe replay.

## Automation and approved tools

Triggers: lead.created, lead.updated, deal.created, deal.stage_changed, task.overdue, message.received, campaign.completed. Conditions allow eq/ne/gt/lt on an explicit field allowlist. Actions: create_task, update_lead, update_deal, add_note, send_email, assign_owner and invoke_ai. Arguments use declared schemas and bounded `$event` substitution; arbitrary code, SQL and dynamic evaluation are absent.

Edits produce immutable revisions and disable the workflow until explicitly enabled. Every execution stores the accepted version/snapshot, status, attempts and error code. Current owner permissions and automation entitlement are checked again at execution; event chains are capped at depth three. CRM actions share the same permission-checked services with AI tools.

Approved tool names: search_leads, get_customer, get_pipeline, create_task, update_lead, create_note, draft_email. Mutations require idempotency; draft_email creates a draft only. Tools cannot execute arbitrary SQL or bypass tenant/RBAC checks.

## Providers and OAuth

Gmail and Outlook have concrete HTTP adapters for connect, token refresh, health check, bounded inbox sync and send. They use fixed official API hosts and server-side configuration. OAuth state is user/tenant/integration bound, hashed, ten-minute expiry and single-use; PKCE verifier and credentials are encrypted independently. Disconnect purges local credentials, with best-effort Gmail remote revocation; Outlook reports remote revocation unavailable. Status responses do not expose tokens. Legacy integration validation now checks a real access token with the adapter; the old raw sync API returns 410 with the replacement route.

| Provider | Implementation status |
| --- | --- |
| Gmail | OAuth, refresh, health, sync and send HTTP contracts; real provider IDs retained |
| Outlook | OAuth, refresh, health, sync and send HTTP contracts; sendMail 202 has no message ID |
| WhatsApp, Meta, Instagram, LinkedIn, Google Ads, Apollo | Capability entries explicitly unavailable; operations fail closed |

External provider calls are mocked at the transport/provider boundary in tests. No live OAuth account, provider certification or production send is claimed. The generic signed webhook bridge is tested; it is not a claim of Gmail Pub/Sub verification or Microsoft Graph subscription provisioning. Gmail and Outlook send APIs are not assumed to guarantee idempotency.

## Controlled AI and entitlements

Six capabilities use the existing AI Gateway: lead_score, lead_summary, next_best_action, reply_analysis, campaign_draft and proposal_draft. Inputs use scoped facts, outputs use strict structured schemas, scores/confidence are bounded, and prompt data cannot authorize tools. Score/summary update their permitted fields; recommendations and campaign/proposal content stay drafts. Proposal drafting creates an existing Proposal entity with provenance. AI hooks await explicit approval and batches are capped at 25 with atomic quota checks.

Usage includes the gateway ledger, tokens, configured known cost, failures, jobs and audit events. Unknown pricing is reported as unknown, never zero-cost certainty. CRM_AI_PROVIDER/MODEL/BASE_URL/API_KEY must be explicitly configured; absent configuration produces a visible failure. Existing gateway fallback facilities remain, while this deployment selects one configured compatible route.

The existing EntitlementService meters users, integrations, campaign launches, messages, attachment metadata storage, automation and AI credits at service boundaries. Administrative plan/entitlement setup remains required. No payment lifecycle was implemented. Mutating APIs additionally use an atomic Redis rate limit (120 per user/tenant/minute, 100 per unauthenticated ingress IP/minute); Redis failure denies writes rather than bypassing protection.

## Analytics, search and frontend integration

Analytics views: dashboard, pipeline, conversion, campaigns, activity and ai. They include customer/deal/task counts, currency-separated pipeline value, lifecycle conversion, recipient outcomes, user activity, first-response samples and AI usage/cost visibility. Date filters are UTC-aware; metric-specific scope is returned, including all-time response-time scope. Collected events are idempotent.

PostgreSQL ranked full-text search covers leads, contacts, companies, deals, tasks, notes, conversations, messages, campaigns and agents, with permission filtering, snippets and bounded pagination. Customer and timeline reads are bounded to 200 related objects per section; search considers at most 100 candidates per entity. Search total describes that candidate set, not an unbounded corpus count.

The frontend contract contains request examples, permissions, asynchronous states, failure behavior and each intended screen flow. The 53 added tests cover these contracts using real PostgreSQL/RLS and Redis, including an executing Celery worker; only external providers are mocked. No new frontend design was supplied or integrated in this checkpoint.

## Setup and remaining limits

Use Python 3.11+, PostgreSQL 16 and Redis 7. Install `pip install -e '.[test]'` for validation. Migrate with the privileged migration role (`alembic upgrade head`), provision runtime credentials (`python scripts/provision_runtime.py`) and run API/workers with the restricted runtime role. Preserve Checkpoint 2 production guards, independent JWT/Fernet keys and database-role separation. See `docker-compose.production.yml` for API, worker, scheduler and migration services.

Inject CRM_GMAIL_* or CRM_OUTLOOK_* OAuth configuration and registered HTTPS callbacks, CRM_PUBLIC_BASE_URL for unsubscribe links, and optional CRM_AI_* model configuration into both API and workers. Secrets belong in deployment configuration, not integration JSON or source. Provision the tenant's entitlements before enabling paid features. Start the existing Celery worker and Beat so queued jobs progress. `python scripts/validate_openapi.py` exports `evidence/openapi.json` without provider calls.

Remaining limits: provider credential/certification and production deployment checks are pending; six non-mail adapters are unavailable; inbound attachments store metadata only and outbound attachment sending is rejected; Outlook sync uses bodyPreview; unread state is shared at conversation level; sequence scheduling uses relative UTC delays; external ambiguous sends require reconciliation; Customer 360/search are bounded as described; AI needs model configuration; no arbitrary workflows, autonomous sales agent, lead purchasing, payments or live mass outreach. These are explicit operational limits, not simulated successes.
